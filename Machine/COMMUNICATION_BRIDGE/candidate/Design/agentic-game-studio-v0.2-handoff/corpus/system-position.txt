The Corpus, Agentic Structure, and Architecture v1.2 sit around the game project. They are the studio's operating infrastructure, not the game or its content.

The game project contains the actual design, source code, assets, runtime, and builds. The three systems govern how those things are created, modified, verified, and delivered.

## 1. The complete structure

STUDIO OPERATING SYSTEM

Corpus · Architecture v1.2 · Agentic Structure

GAME PROJECT

GAME DESIGN

GDD · Rules · Mechanics · Worlds · Maps · Progression · Balance

SOURCE CODE

Engine · Gameplay · AI · Networking · Systems · Tools

DESIGN ASSETS

Concept art · References · Blockouts · Source models · Audio sources

RUNTIME ASSETS

Meshes · Materials · Animation · Audio · Levels · Data

BUILD + TEST + PLAYTEST

Compile · Cook · Execute · Measure · Verify

GAME RELEASE

This is a logical ownership diagram, not a literal filesystem or dependency graph.

## 2. Where everything actually lives

| Element                                    | Location and authority                                                  |
| ------------------------------------------ | ----------------------------------------------------------------------- |
| Studio doctrine and architectural rules    | Corpus, backed by controlled authoritative records                      |
| Game design documents                      | Project `design/`, indexed by the Corpus                                |
| Game source code                           | Project Repository                                                      |
| Source art and authored assets             | Project asset source, under version control or controlled asset storage |
| Runtime assets                             | Project Runtime content                                                 |
| Agent instructions and execution contracts | Agentic execution layer                                                 |
| Tasks and execution receipts               | Project Task Manager and durable records                                |
| Build and test outputs                     | Project production outputs                                              |
| Shipped game                               | Immutable Release artifact                                              |

The Corpus does not replace the game repository. It makes the relevant knowledge discoverable and applicable to agent tasks.

## 3. How design and assets connect to production

Take a single game feature: a powered security door.

DESIGN SPECIFICATION

Door behavior, power requirements, player interaction

SOURCE ASSETS

Door model, animations, sounds, material sources

SOURCE CODE

Door state machine, power interface, interaction logic

RUNTIME CONTENT

Integrated door Blueprint, meshes, audio and data

BUILD + TEST

Compile, cook, test state transitions and interactions

RELEASE

Verified executable game containing the door

The three studio systems operate across this process:

Corpus: Supplies the approved door design, relevant engine contracts, art requirements, and previous decisions.

Agentic Structure: Assigns design, engineering, and asset work to agents with appropriate capabilities and bounded permissions.

Architecture v1.2: Controls where outputs belong, how source is integrated, how builds are produced, how results are verified, and what can enter a release.

## 4. The distinction that matters

There are actually three different kinds of information:

Intent: What the game should be. This includes GDDs, gameplay specifications, art direction, and approved design decisions.

Implementation: What has actually been built. This includes source code, Blueprints, models, levels, configurations, and executable behavior.

Evidence: What has been demonstrated to work. This includes test results, playtest findings, build receipts, and acceptance records.

They must remain separate.

A GDD saying that a door should open in two seconds does not prove the runtime does so.

A Blueprint implementing a two-second animation does not prove the door behaves correctly under network latency or power loss.

A passing test proves only the behavior exercised under its declared conditions.

The operating architecture connects all three without confusing them.

## 5. The missing connection: game identity

One additional contract would materially improve the combined architecture.

The project needs stable identities linking design requirements to implementation and evidence.

For example:

```
feature:
  id: "SECURITY_DOOR_001"

  design:
    specification: "DOOR_SPEC_003"
    revision: "7"

  implementation:
    source: "DoorController"
    runtime_asset: "BP_SecurityDoor"

  verification:
    tests:
      - "DOOR_POWER_LOSS"
      - "DOOR_NETWORK_SYNC"
      - "DOOR_OBSTRUCTION"

  status: "verified"
```

This is a proposed extension, not a contract already fully defined in v1.2.

It allows an agent to answer three essential questions:

- What was this feature intended to do?
- Which exact implementation realizes that intent?
- What evidence establishes that it works?

Without those links, the studio may have excellent task management and version control while still losing the relationship between design and actual game behavior.

## Verdict

The game project is the product. The three systems form the production machine around it.

I would organize the studio around one persistent project identity that connects four authoritative surfaces:

Design → Source and Assets → Runtime → Release

The Corpus resolves knowledge across them. Agents perform bounded work on them. Architecture v1.2 protects their transitions.

That is the point where the three documents become an operational agentic game development studio rather than three separate specifications.
